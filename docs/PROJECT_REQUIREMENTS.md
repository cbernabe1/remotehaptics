# Project Requirements

> **Status:** Approved planning baseline, 2026-10-30; paired remote haptics added 2026-11-01.
> **Source:** `VIBRATION_CONTROL_PLAN.md`, Sections 2, 5, 6, 15, and 19.
> **Implementation status:** MVP UI, Android playback, and paired remote haptics implemented; persistence and iOS remain pending.

## 1. Product Summary

Vibration Control is a Flutter application for Android and iOS that lets a user test, adjust, and save haptic effects generated by the application itself. Two phones can optionally pair so one user can adjust the other phone's app-generated haptics over an internet relay.

The product is an in-app haptics laboratory. It is not a system-wide vibration controller and must never claim to change call, SMS, alarm, notification, or third-party application vibration.

## 2. Objectives

- Let a user hear and compare app-generated haptic effects.
- Let a user adjust requested output strength where the device supports it.
- Let a user save and reload preferred configurations locally.
- Report device capabilities truthfully.
- Explain platform limitations clearly.
- Protect privacy by keeping local features offline, collecting no user data, and keeping remote sessions ephemeral.
- Let a host explicitly approve a paired controller and end a remote session at any time.

## 3. Users and Use Cases

### Primary user

A user who wants to test how strong or weak an app-generated haptic effect feels on their own device.

### Core use cases

1. Open the app and see whether haptics are available.
2. Play a safe default test pulse.
3. Change the duration and requested output level.
4. Compare built-in soft, normal, and strong presets.
5. Save a preferred configuration and use it after restarting the app.
6. Understand which controls are limited by the device or operating system.
7. Pair two phones through a short-lived room code so one user can adjust the other phone's app haptics after approval.
8. End a remote session immediately from either phone.

## 4. In Scope

- App-generated haptics while the application is in the foreground.
- Android amplitude control where `hasAmplitudeControl()` reports support.
- iOS Core Haptics intensity on supported iPhones.
- Capability detection and disclosure.
- One-shot pulses and built-in multi-pulse presets.
- Local settings and user presets.
- Capability and limitation guidance in Settings.
- Offline operation for local features, accessibility, and privacy.
- Paired remote haptics through a user-deployed WebSocket relay, with host approval, foreground-only operation, and no accounts.
- Automated tests and physical-device validation.

## 5. Out of Scope

- Global Android or iOS vibration intensity.
- Call, SMS, alarm, or third-party notification vibration.
- Another application's haptics.
- Direct motor voltage, frequency, or overdrive control.
- Exceeding hardware limits.
- Root, jailbreak, privileged permissions, or hidden OEM APIs.
- Accounts, cloud sync, AI, analytics, or advertising.
- Background haptic automation or scheduling.
- Remote control without explicit host approval or outside an active session.
- Persisting relay messages, room history, or user identity.
- Notification-channel customization in the MVP.
- A full user-authored pattern editor in the MVP.
- Localization beyond English in the MVP.

## 7. Functional Requirements

| ID | Requirement | Acceptance criteria |
|---|---|---|
| FR-01 | Detect and display capabilities | Settings shows actuator availability, amplitude/intensity support, pattern support, stop support, platform, and OS. Unknown values are labeled unknown. |
| FR-02 | Play a safe test pulse | Default effect is short and moderate; stop works; unsupported hardware shows a clear message. |
| FR-03 | Configure duration | Graph hold time controls the live pulse up to 5000 ms; chips select the Play test and saved-preset length. Invalid values are prevented or rejected. |
| FR-04 | Configure output strength | Home's graph control adjusts app-generated amplitude or intensity only where supported; unsupported controls are disabled or explained. |
| FR-05 | Stop playback | Stop cancels active playback where supported and returns the UI to idle. |
| FR-06 | Play built-in presets | Presets produce the documented effect on supported hardware. |
| FR-07 | Manage user presets | Save, load, rename, and delete with confirmation; data persists across restart and invalid data does not crash the app. |
| FR-08 | Explain limitations | UI distinguishes app-generated effects from system-wide vibration and explains call/SMS/alarm restrictions. |
| FR-09 | Settings | User can set duration and strength on Home, disable app haptics in Settings, and reset local data. |
| FR-10 | Error feedback | Unsupported, unavailable, busy, interrupted, and invalid-input states produce actionable messages. |
| FR-11 | Lifecycle handling | Playback stops when the app is backgrounded and the UI recovers on return. |
| FR-12 | Accessibility | Controls have semantic labels, 48dp minimum targets, adequate contrast, scalable text, and non-haptic equivalents. |
| FR-13 | Offline operation | Local functionality works in airplane mode with no network dependency; remote pairing requires a relay. |
| FR-14 | Bounded playback | Duration, segments, repeats, and total pattern length are capped; no infinite repeat in the MVP. |
| FR-15 | Platform disclosure | UI states whether a feature is Android-only, iOS-only, or device-dependent. |
| FR-16 | Create remote room | Host connects to a configured relay and receives a six-digit room code that expires when unused. |
| FR-17 | Approve remote control | Controller can join only with an active code; host must accept before any haptic command is accepted. |
| FR-18 | Live remote haptics | Controller strength changes are relayed to the host and played through the normal app haptics service; release stops playback. |
| FR-19 | End remote session | Either phone can leave; disconnect, backgrounding, expiry, and errors stop playback and clear the session. |
| FR-20 | Relay privacy | Rooms and names are memory-only, messages are capped, attempts are rate-limited, and sessions expire. |

## 8. Nonfunctional Requirements

| Area | Requirement |
|---|---|
| Offline | Local haptics, settings, and presets require no backend, account, or network. Remote pairing requires a relay. |
| Remote transport | WSS in production, host approval for every session, foreground only, 30-minute session cap, and no relay persistence. |
| Startup | Cold start target under 2 seconds on a mid-range test device. |
| Battery | No background polling, wakelocks, or continuous vibration; stop native playback when idle. |
| Reliability | Unsupported hardware, rapid taps, invalid input, interruptions, and lifecycle changes must not crash the app. |
| Accessibility | TalkBack and VoiceOver labels, 48dp targets, contrast, scalable text, and information not conveyed by haptics alone. |
| Privacy | No PII, analytics SDK, or advertising. Network calls occur only for a user-started remote session; no room or message history is stored. |
| Maintainability | Thin native bridge, typed errors, unit and widget tests, clean analyzer, documented decisions. |
| Cross-platform | Shared Flutter UI with platform differences isolated behind one service interface. |
| Error handling | Native failures become typed Dart errors with user-safe messages. |
| Testing | Unit, widget, integration, and physical-device testing. Emulator output is not proof of haptic strength. |
| Device coverage | At least two Android devices with different amplitude capabilities; one Core Haptics iPhone. |

## 9. Validation Rules

| Rule | Value |
|---|---|
| Vibration duration | 20-5000 ms |
| Pause after segment | 0-5000 ms |
| Segments per preset | 1-10 |
| Repeat count | 1-5 |
| Total pattern duration | 30 seconds maximum, including pauses and repeats |
| Requested strength | 1-100 percent |
| Preset name | 1-40 characters after trimming |
| User presets | 50 maximum in the MVP |
| Infinite repeat | Not allowed |
| NaN and infinity | Rejected |
| Android amplitude mapping | `round(percent * 255 / 100)`, clamped to 1-255, only when supported |
| iOS intensity mapping | `percent / 100`, clamped to 0.01-1.0 |
| Unsupported amplitude | Disable the control or use an explicit on/off fallback; never silently imply amplitude control |
| Remote room code | Exactly six digits |
| Remote display name | 1-24 characters after trimming |
| Remote strength | 1-100 percent |
| Remote hold | 5000 ms maximum |
| Remote message size | 4096 bytes maximum |
| Remote room lifetime | 10 minutes waiting, 60 seconds approval, 30 minutes active |

## 10. MVP Definition of Done

- All MVP functional requirements are implemented.
- Capability reporting is truthful on every test device.
- Test pulse, duration, output strength, presets, and persistence work.
- Paired remote haptics require host approval and can be ended from either phone.
- Unsupported hardware and unsupported amplitude are handled explicitly.
- No UI, metadata, or documentation claims system-wide control.
- Automated unit, widget, and integration tests pass.
- Analyzer and lint are clean.
- Physical-device logs exist for at least two Android devices and the available iPhone.
- Background, interruption, and rapid-tap tests pass.
- Accessibility and privacy reviews are complete.
- Release build installs and runs on a clean device.
- Documentation is updated and the user signs off.

## 11. Deferred Features

- Full multi-segment pattern editor with per-segment strength.
- Looping and infinite vibration.
- Pattern import, export, and sharing.
- Advanced diagnostics such as frequency, primitives, and sharpness curves.
- OEM-specific integrations.
- Notification-channel customization.
- Background automation and scheduling.
- Cloud sync, accounts, analytics, AI, and social features.
- Localization beyond English.
- Custom themes, calibration wizard, widgets, and quick-settings tiles.

## 12. Constraints and Assumptions

- Flutter stable is used.
- Android minimum is API 26; iOS minimum is 13.0.
- Android-first delivery; iOS follows after Android validation.
- macOS, Xcode, and a physical iPhone 8+ are available for later iOS work.
- The current development host is Windows, so iOS builds require a separate Mac or remote macOS environment.
- Internal APK and TestFlight distribution is sufficient for the MVP.
- The working app name is Vibration Control.
- The placeholder package/bundle ID is `com.example.vibration_control` until a final reverse-DNS ID is confirmed.
- A lightweight custom visual theme (violet/mint/coral palette, Manrope typography, rounded icons) is used for the MVP.

## 13. Current Exceptions

- The Android test phone is currently disconnected, so reinstall and remaining lifecycle validation are deferred.
- A second, non-amplitude Android test device is not confirmed.
- iOS build and device validation cannot run on the current Windows host.
- The Flutter-generated iOS deployment target is 15.0 and must be reconciled with the approved iOS 13 minimum before iOS work.
- Chrome preview playback is simulated and is not proof of haptic behavior.
