# Decision Log

> **Status:** Approved planning baseline, 2026-10-30.
> **Format:** Architecture Decision Record, concise.
> **Rule:** Append new decisions; do not remove history. Supersede rather than rewrite.

## D-001 - Product scope is in-app haptics only

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** No public API allows an ordinary app to change system-wide vibration intensity, call/SMS/alarm vibration, or another app's haptics.
- **Decision:** The product is an in-app haptics laboratory. It adjusts effects generated by this application only.
- **Consequences:** The UI, documentation, and metadata must state the boundary. System settings guidance is allowed; claims of system control are prohibited.
- **Alternatives rejected:** System-wide vibration controller; notification vibration editor; hidden or privileged API use.

## D-002 - Android-first delivery

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Android can be built on the current Windows host. iOS requires macOS and Xcode. Android has the richest public haptics API surface.
- **Decision:** Implement and validate Android first. Implement iOS after Android's core loop is stable.
- **Consequences:** Android is the primary MVP platform. iOS code and validation are planned but not part of the first implementation slice.
- **Alternatives rejected:** Blocking all work until iOS tooling is ready; shipping only an unvalidated iOS build.

## D-003 - Smaller MVP with deferred pattern editor

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The full pattern editor adds significant UI, validation, native, and testing scope.
- **Decision:** MVP includes capability detection, test pulse, duration, output level, three built-in presets plus one two-pulse preset, local save/load, capability and limitation guidance in Settings, and tests. The full pattern editor is deferred.
- **Consequences:** The core loop ships sooner. Pattern editing remains a post-MVP feature.
- **Alternatives rejected:** Full pattern editor in the first release.

## D-004 - Minimum OS versions are Android 8 and iOS 13

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Android API 26 provides `VibrationEffect`. Core Haptics requires iOS 13.
- **Decision:** Android `minSdk` is 26; iOS deployment target is 13.0.
- **Consequences:** The app can use the stable waveform API and Core Haptics without unnecessary compatibility layers.
- **Alternatives rejected:** Android 6 fallback; iOS 12 fallback.

## D-005 - The UI uses a 1-100 app output level

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Amplitude and intensity are normalized parameters, not perceptually linear volume controls. Android uses 1-255; iOS uses 0.0-1.0.
- **Decision:** Expose one platform-neutral 1-100 "app output level" with a disclaimer. Map to native values only when the capability exists.
- **Consequences:** The UI avoids implying that 50 percent equals half the physical strength. Unsupported controls are disabled or explained.
- **Alternatives rejected:** A 1-10 scale; exposing Android's 1-255 scale across platforms.

## D-006 - Riverpod and SharedPreferences are the state and persistence stack

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The app has small local data, a few controllers, and no relational queries.
- **Decision:** Use Riverpod without code generation and `shared_preferences` with a versioned JSON envelope.
- **Consequences:** Dependency injection and testing remain simple. SQLite migrations are unnecessary for the MVP.
- **Alternatives rejected:** Bloc with SharedPreferences; Provider with SQLite; Hive, Isar, or secure storage.

## D-007 - Distribution starts with internal builds

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The MVP needs fast device testing and does not yet need public store distribution.
- **Decision:** Use internal APK and TestFlight builds initially.
- **Consequences:** Store accounts, review, screenshots, and public metadata are not MVP blockers. Store release remains a later decision.
- **Alternatives rejected:** Public Play Store and App Store release in the MVP.

## D-008 - Working name and placeholder identifier

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The final brand and reverse-DNS identifier are not confirmed.
- **Decision:** Use "Vibration Control" as the working name and `com.example.vibration_control` as the placeholder package and bundle identifier.
- **Consequences:** The identifier must be replaced before release signing or store submission. Renaming after release is more expensive.
- **Alternatives rejected:** Keeping `personalapp`; delaying planning until branding is final.

## D-009 - Physical devices are required for haptic acceptance

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Emulators and simulators cannot reproduce real haptic hardware behavior or perceived strength.
- **Decision:** Accept haptics only after physical-device testing. Emulators are for UI and unsupported-state testing.
- **Consequences:** Release is blocked without at least one physical Android device. iOS release requires a Core Haptics iPhone.
- **Alternatives rejected:** Accepting successful builds as proof of haptic behavior.

## D-010 - Baseline accessibility only

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The MVP is English-only and does not yet need a full accessibility audit.
- **Decision:** Provide semantic labels, 48dp targets, contrast, scalable text, and basic TalkBack/VoiceOver support.
- **Consequences:** A full accessibility audit and additional languages are deferred.
- **Alternatives rejected:** Full audit and localization in the MVP.

## D-011 - Use a native MethodChannel bridge

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Flutter `HapticFeedback` lacks duration, amplitude, and pattern control. The `vibration` package has unsuitable usage classification and error-reporting limits.
- **Decision:** Own a small `MethodChannel` contract for capabilities, play, and stop.
- **Consequences:** Native code is required on both platforms, but capability reporting and fallback behavior remain under our control.
- **Alternatives rejected:** Flutter built-in haptics; `vibration` package as the production core; Pigeon for the MVP.

## D-012 - No backend, accounts, analytics, or advertising

- **Status:** Accepted
- **Superseded in part by:** D-023 for paired remote haptics only.
- **Date:** 2026-10-30
- **Context:** The product has no server-side requirement and should be private by default.
- **Decision:** Keep the app fully offline and local-only.
- **Consequences:** No privacy policy complexity from data collection. Core features must work in airplane mode.
- **Alternatives rejected:** Cloud preset sync; analytics; account system.

## D-013 - Persist one versioned JSON envelope

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Settings and a small number of presets need local persistence with a safe migration path.
- **Decision:** Store `schemaVersion`, `settings`, and `presets` in one `shared_preferences` value.
- **Consequences:** Loads must validate and preserve unknown future data. Import/export can reuse the envelope later.
- **Alternatives rejected:** Separate unversioned keys; SQLite; raw file storage as the primary store.

## D-014 - Cap playback with explicit limits

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Unbounded vibration is a safety, battery, and UX risk.
- **Decision:** Limit vibration to 20-5000 ms per segment, 1-10 segments, 1-5 repeats, and 30 seconds total. No infinite repeat in the MVP.
- **Consequences:** The app cannot be used to create an indefinitely running vibration.
- **Alternatives rejected:** User-defined unlimited duration or looping.

## D-015 - One active playback session

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** Overlapping native playback creates confusing output and inconsistent stop behavior.
- **Decision:** Allow one active session. A new user-initiated test cancels the previous test; the UI also debounces rapid taps.
- **Consequences:** Playback state is simple to reason about and test.
- **Alternatives rejected:** Multiple concurrent sessions; returning busy for every new test.

## D-016 - Stage 1 and Stage 2 only are authorized

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The user approved the plan and authorized planning documents plus the environment baseline.
- **Decision:** Do not write application code or modify platform configuration until Stage 2 exits and Stage 3 is explicitly started.
- **Consequences:** Documentation and environment checks can proceed; scaffolding, dependencies, and native code cannot.
- **Alternatives rejected:** Starting implementation before verifying the toolchain.

## D-017 - iOS needs a separate macOS build environment

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The current host is Windows 11. Xcode cannot run on Windows.
- **Decision:** Treat macOS, Xcode, and the physical iPhone as a separate later-stage environment.
- **Consequences:** Android validation can proceed on the current host. iOS build and haptic validation are blocked until the macOS environment is verified.
- **Alternatives rejected:** Claiming iOS readiness from Windows; relying only on an iOS simulator.

## D-018 - Chrome preview is used for UI work before native playback

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The physical Android device is not connected, but Flutter Chrome and Android tooling are available.
- **Decision:** Build and review the MVP UI in Chrome with a simulated haptics service. Defer real Android and iOS haptic validation.
- **Consequences:** UI and navigation can progress now. Real haptics, capability truth, lifecycle behavior, and device variability remain unvalidated until native playback exists and a physical device is tested.
- **Alternatives rejected:** Waiting for the phone before any UI work; treating Chrome playback as real haptic validation.

## D-019 - Web is enabled as a development and preview target

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The project was created without a web target, but Chrome is the available UI preview device.
- **Decision:** Add the Flutter web target and use it for UI review only.
- **Consequences:** `flutter run -d chrome` and `flutter build web` work. Web is not a supported haptics delivery target and must not be described as one.
- **Alternatives rejected:** Adding native haptics before reviewing the UI; using only Windows desktop.

## D-020 - The preview service reports simulated capabilities

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** A capability report with no actuator would disable most controls and prevent UI review.
- **Decision:** The preview service reports amplitude-capable simulated playback, plus explicit warnings and a `Web preview` platform label.
- **Consequences:** The UI can be exercised in Chrome, but the report is not a real device claim. It must be replaced before release.
- **Alternatives rejected:** Disabling all controls in the preview; silently presenting simulated values as real hardware capabilities.

## D-021 - Package identity uses the approved placeholder

- **Status:** Accepted
- **Date:** 2026-10-30
- **Context:** The initial project used `personalapp` and `com.example.personalapp`.
- **Decision:** Use Dart package name `vibration_control`, Android namespace/application ID `com.example.vibration_control`, and iOS bundle ID `com.example.vibration_control`.
- **Consequences:** The identity is consistent across platforms. The final reverse-DNS identifier still must replace the placeholder before release.
- **Alternatives rejected:** Keeping the generic `personalapp` identity.

## D-022 - Visual direction uses a pulse palette, rounded icons, and Manrope

- **Status:** Accepted
- **Date:** 2026-11-01
- **Context:** The original UI used a single indigo seed color, default typography, and mixed icon styles. The app is a haptics laboratory, so the visual language should feel tactile, energetic, and modern.
- **Decision:** Use a violet primary, mint secondary, and coral tertiary palette with matched light/dark surfaces; rounded Material icons; rounded cards and navigation; and the bundled Manrope typeface.
- **Consequences:** The UI has a consistent modern identity without a runtime font fetch. The Presets page is removed and its library stays on Home to keep the navigation focused.
- **Alternatives rejected:** Keeping the seed-only default theme; adding a runtime Google Fonts dependency; keeping a separate Presets tab.

## D-023 - Paired remote haptics use an ephemeral WebSocket relay

- **Status:** Accepted
- **Date:** 2026-11-01
- **Context:** The user wants one phone to adjust app-generated haptics on another phone over the internet. This partially supersedes D-012's no-backend clause while preserving the no-account, no-analytics, and no-persistence rules.
- **Decision:** Add a Node.js WebSocket relay under `relay/`, pair with six-digit room codes, require host approval for every controller, and relay only live strength/duration plus host playback status. Use in-memory rooms with expiry and rate limits.
- **Consequences:** Local mode remains offline. Remote mode requires a reachable relay, both apps in the foreground, and explicit approval. No messages, identities, or room history are stored. Public deployments must use TLS.
- **Alternatives rejected:** Direct peer-to-peer networking; unapproved controller access; persisted room history; accounts or cloud sync; exposing a general-purpose remote API; background automation.
